# Bebragram 1263: Tor

Основа: `890ebb918d152e26da8b7929cf888fba5ed1282d`, совпадает с последним
проверенным релизом `v12.10.0-1262` от 29 сентября 2026.

## Что подтвердилось

1. **WebTunnel/uTLS.** IPtProxy 5.5.1 использует upstream uTLS 1.8.2, хотя
   Lyrebird ожидает форк shelikhoo/utls-temporary. Замена в go.mod зависимости
   игнорируется Go. Локальный тест исходной uTLS падает на seed 2 с
   `tls: CurvePreferences includes unsupported curve`. Тот же тест с заменой
   проходит 128/128. Сервер разрешает TLS 1.2/1.3 и предпочитает ML-KEM.
   Ошибки `protocol version not supported` из приведённого чужого теста
   отдельно не доказывают неисправность мостов: TLS-1.3-only сервер отвергает
   randomized ClientHello, которые предлагают максимум TLS 1.2.
2. **Рестарт до ServiceConnected.** Старый код отвязывает сервис, ещё не получив
   Binder, а затем может объявить его остановленным только по отсутствию Binder.
   Само по себе это не подтверждает смерть процесса. Запуск следующей сессии
   разрешён теперь только после death callback старого Binder. Подключение до
   остановки, отключение до подключения и повторные уведомления проверены в JVM.
3. **Потенциальное зависание UI.** `connectProxy(tor.socksPort)` делал синхронный
   Binder-запрос с главного потока. Порт теперь считывается на controlWorker.
   Это реальный риск в коде, но причину конкретного зависания телефона без ANR/
   logcat установить нельзя.
4. **Мосты.** Ошибка Tor не определяет виновный мост; прежний код банил все
   выбранные хосты. Теперь старые строки лишь получают меньший приоритет,
   кандидаты выбираются из всего списка, число повторных попыток ограничено.
   HTTPS GET проверяет доступность адреса, успешный bootstrap проверяет мост.

## Дополнительные исправления

- Автозапуск по умолчанию true; сохранённое явное отключение учитывается.
  Сам Tor-прокси пользователь включает отдельно. Временная ошибка больше не
  сбрасывает сохранённое включение Tor.
- Binder/control исключения обрабатываются, сообщения старой сессии не меняют
  новую. Поле generation видимо между потоками.
- Загрузка мостов и опрос Tor имеют отдельные очереди. Завершившийся старый
  запрос не перезаписывает введённые мосты и не перезапускает отключённый Tor.
- TorHostService гарантирует выход отдельного процесса даже при зависании
  синхронного shutdown в библиотеке. Новый процесс ожидает подтверждения выхода.
- Подготовка сервиса и bootstrap получают отдельные таймауты: 60 и 120 секунд.
- Исправлен разбор вставленных Snowflake-строк с префиксом `Bridge ` и параметров с табуляцией.
- Версия сборки увеличена до 1263; все CI-сборки устанавливают Go и NDK для
  пересборки IPtProxy с закреплённым форком. Готовый Maven AAR заменён задачей
  `buildTorTransport` с отслеживанием входных файлов.

- `Tools/tests/tor-jvm/run.sh`: все сценарии жизненного цикла проходят.
  Это реальные изменённые классы с JVM-заменами Android/Telegram, а не запуск
  Android на устройстве.
- AAR собран для armeabi-v7a, arm64-v8a, x86 и x86_64; `go version -m`
  подтверждает нужный replace в libgojni.so. arm64 ELF выровнен на 16 КБ.

  Проверка общего графа `compileDebugKotlin --dry-run` остановилась на отсутствующих
  SDK Build-Tools 36/platform package metadata и лицензиях локальной среды.

  конкретное зависание, нужен ANR/logcat телефона.
